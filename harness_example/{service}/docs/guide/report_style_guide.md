# 보고서 작성 가이드

> reports/ 에 들어가는 문서의 **공통 양식**. 반복 작업의 규약이므로 guide/에 둔다.
> (1회성 사실·실행법은 reference/, 분석 결과 자체는 reports/)
> HTML로 공유용 보고서를 만들 땐 `report-design-system.html`의 디자인 토큰을 재사용한다.

---

## 1. 파일명 규칙

```
<주제>_<유형>_YYYYMMDD.md
```
- 유형: `report`(완료 보고) · `analysis_report`(분석) · `research`(리서치, 날짜 생략 가능)
- 예: `{주제}_analysis_report_{YYYYMMDD}.md`

---

## 2. 필수 헤더 (문서 맨 위)

```markdown
# <제목>

| 항목 | 내용 |
|------|------|
| 작성일 | YYYY-MM-DD |
| 작성자 | <팀/이름> |
| 유형 | 성능/장애 분석 · 기능 · 아키텍처 · 리서치 중 하나 |
| 대상 | <분석 대상 컴포넌트> |
| 상태 | 분석 완료 / 진행 중 / 적용 완료 |
```

---

## 3. 유형별 섹션 구조

| 유형 | 권장 섹션 |
|------|----------|
| 성능/장애 분석 | 요약(TL;DR) → 배경/측정 → 원인 분석 → 개선안(우선순위표) → 후속 |
| 기능 | 요약 → 구현 범위 → 변경 파일 → 검증 결과 → 잔여 과제 |
| 아키텍처 | 요약 → 현행 문제 → 제안 구조 → 트레이드오프 → 마이그레이션 |
| 리서치 | 질문 → 후보 비교표 → 권고 → 근거/출처 |

---

## 4. 규칙

- **TL;DR 필수** — 결론을 맨 위 3줄 이내로.
- 측정치는 표로(정상 vs 사고 시 같은 대비 구조).
- 개선안은 **우선순위(P0/P1/P2) + 기대효과** 표로.
- 보고서에 실행 계획을 길게 쓰지 말 것 → `tasks/`로 분리하고 링크만.
- 적용·검증 완료 시 `archive/reports/`로 이동하고 INDEX에 사유 기록.
